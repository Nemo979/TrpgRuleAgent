# TrpgRuleAgent V2.2 可行性与执行方案

更新时间：2026-08-08

状态：可执行基线

适用范围：V2.1 稳定性收口之后，面向少量可信用户的 Web/Python 正式链路

> 本文是 V2.2 及后续智能体改造的**唯一总体执行依据**。
>
> [项目现状](project-status.md) 记录已经完成和仍未完成的事实；
> [架构文档](architecture.md) 记录当前正式架构；
> [近重复资料处理机制](near-duplicate-retrieval.md) 只描述检索多样性的专项设计；
> [答案级评测](answer-evaluation.md) 只描述验收工具。它们不各自定义另一套实施顺序。

## 1. 结论

当前项目**不适合进行一次性的“完整 Agent 平台重构”**，也不应照通用方案从 Conversation Manager、
Router、Planner、Memory、Multi-Agent 重新建设一遍。

原因是当前正式链路已经具备：

- 按 `libraryId` 隔离的多系统、多版本规则库；
- 服务端串行工具编排与循环收敛；
- `search_rules` / `read_rules` 证据读取和引用注册；
- 固定搜索、读取和证据字符预算；
- `ConversationState` 结构化角色状态；
- 规则优先的查询增强与四类问题意图；
- 构筑问题的有限查询计划；
- 取证阶段与最终回答阶段隔离；
- 检索评测和答案级评测。

适合当前项目的路线是：

```text
基线收拢
  → 只读测量（近重复 + Token/Context/Latency）
  → 根据数据选择证据优化
  → 上下文管理
  → 受限复杂任务规划
```

下一阶段命名为：

> **V2.2 可观测性与证据管理**

它首先建立测量和回归基线，不立即改变线上排序，也不立即增加新的 LLM 调用。

## 2. 设计输入及其角色

### 2.1 当前代码与项目文档

当前代码、`project-status.md` 和 `architecture.md` 是事实来源。任何方案描述与当前实现不一致时，
以代码和当前状态为准。

### 2.2 近重复专项方案

`near-duplicate-retrieval.md` 被保留为 V2.2 的专项子方案。可直接采用的部分包括：

- Phase0 只读审计；
- `ruleLibraryId` 硬隔离；
- `derivedSemanticKey`；
- trigram shingle Jaccard；
- `dedupSafetyVeto`；
- 簇代表优先、次级候选补齐；
- `enable_diversity` 默认关闭；
- Phase2/3 才处理来源关系和 `possibleDisagreement`。

该专项方案不能越过本文的阶段门直接进入线上排序开发。

### 2.3 通用智能体改造方案

外部《TRPG Agent 智能体系统改造迭代方案》只作为长期能力参考，吸收以下原则：

- 确定性能力优先由代码实现；
- LLM 只处理规则难以稳定完成的语义任务；
- 简单问题保持直接 RAG；
- 复杂问题才进入任务拆解；
- 先控制 Context 和 Evidence，再考虑 Planner；
- 不默认使用 Multi-Agent；
- 保持模块化单服务，不提前微服务化。

其原始十阶段顺序不直接采用，因为 Evidence Budget、Intent、结构化状态、Answer Synthesizer 和
Evaluation 在本项目中已经部分或完整存在。

## 3. 当前基线与不可破坏边界

### 3.1 产品边界

- 正式入口为 React Web + Python App + Python Retrieval。
- 面向少量可信用户，第一版使用共享密码。
- 模型由管理员在服务端配置，浏览器不能提交或读取 API Key。
- 对话只保存在浏览器，服务端不持久化原始问题和回答。
- 一个对话固定绑定一个 `libraryId`、规则系统、版本和创建时 revision。
- 不同系统、不同版本、不同规则库必须隔离。

### 3.2 证据安全边界

- 模型不能用自身记忆替代当前规则库证据。
- 只有经 `read_rules` 真正读取并注册的文档才能成为 `[S1]` 等来源。
- 搜索摘要、历史摘要和结构化状态都不是规则证据。
- 最终回答继续使用“当前问题 + 明确状态 + 本轮已读证据”的干净上下文。
- 优化不能把未读取的相似来源冒充为已读引用。

### 3.3 数据与回滚边界

- 规则正文、索引、源 PDF/CHM 和密钥不得提交到 Git。
- 每次可能改变召回或排序的改造前，必须保存完整、不可变的规则库构建。
- 回滚点至少包含 `documents.jsonl`、向量索引、manifest/build-state、revision 指向和对应代码提交。
- Git tag 不能替代被忽略的本地规则库构建产物。

## 4. 可行性判断

| 能力 | 当前基础 | 技术可行性 | 当前优先级 | 结论 |
| --- | --- | --- | --- | --- |
| 答案级回归 | 已有事实、引用、工具预算和 LLM 裁判 | 高 | P0 | 先合入并作为所有改造的发布门 |
| 近重复 Phase0 | 检索候选≤50、已有评测集 | 高 | P0 | 只读执行，不改线上排序 |
| Token/Context/Latency 计量 | 已有请求 ID、工具状态和模型配置 | 高 | P0 | 先记录聚合指标，不记录正文 |
| 高置信多样性排序 | 有重排后候选和 feature flag 落点 | 中高 | 条件 P1 | 只有 Phase0 证明收益后才实现 |
| 动态 Evidence Budget | 已有固定 `EvidenceBudget` 与意图分类 | 高 | P1 | 在现有预算对象上演进 |
| Conversation Summary | 浏览器保存完整会话、后端会裁剪 | 中 | P1 | 达到阈值才生成，不能成为规则证据 |
| LLM Query Rewrite | 已有规则 Query Rewrite | 中 | P1 后段 | 只作低置信度 fallback |
| 多问题拆解 | 已有有限构筑查询计划 | 中 | P2 | 先支持少数明确任务类型 |
| 通用 Planner/DAG | 可复用现有意图和工具执行 | 中 | P2 | 第一版串行、受限 Schema |
| 并行 Scheduler | Provider 限流和证据合并仍需验证 | 中低 | 延后 | 串行成本被证明后再评估 |
| 跨会话 Memory | 与浏览器本地会话边界冲突 | 低 | 暂缓 | 需单独产品与隐私决策 |
| Multi-Agent | 没有独立权限/工具/模型边界需求 | 低 | 不做 | 当前只会增加复杂度和成本 |
| 微服务拆分 | 当前规模无独立扩缩容需求 | 低 | 不做 | 保持现有服务边界 |

## 6. 分阶段实施方案

### Stage 0：基线收拢

目标：形成后续所有优化可比较、可回滚的正式基线。

工作项：

1. 合并答案级评测实现和相关测试。
2. 提交本文与近重复专项方案。
3. 保存当前 PF1e 完整不可变构建及代码对应关系。
4. 执行 TypeScript、Web build、Python App、Python Retrieval 和答案级基线验证。
5. 推送 `release`；验收后再同步 `main`。
6. 更新 `project-status.md`，移除已经完成但仍写作“待完成”的状态。

完成标准：

- 工作树没有无法解释的中间方案文件；
- 规则库构建可以恢复；
- 当前检索和答案报告可复现；
- release/main 的状态和项目文档一致。

### Stage 1：只读测量

目标：不改变用户答案，回答“真正的瓶颈在哪里”。

#### 1A. 近重复 Phase0

严格按 `near-duplicate-retrieval.md` 执行：

- 对每题 Top-50 做桶内扫描；
- 在同一 `ruleLibraryId` 内做跨桶探索扫描；
- 统计 Top-8 重复占位、独立规则点覆盖和安全否决；
- 模拟两遍排序，但不写回真实搜索结果；
- 从 0.90 开始做阈值实验，不预设线上默认值。

#### 1B. Context/Token/Latency 测量

每轮记录聚合指标：

- 历史估算 Token；
- System、State、Evidence 和输出预留预算；
- 被裁剪消息数；
- 搜索和读取次数；
- 已读文档数及 Evidence 字符/估算 Token；
- 模型决策、检索、读取、最终生成和总耗时；
- 模型返回 usage 时记录 prompt/completion token；未返回时使用保守估算。

隐私要求：

- 不记录原始问题、回答、规则正文、摘要正文或密钥；
- 只记录 request ID、library/model、意图、数值指标、停止原因和查询摘要哈希。

Stage 1 完成后必须召开一次数据评审，不能自动进入 Stage 2。

### Stage 2：证据质量与预算

Stage 2 分为两个可独立启用的子项。

#### 2A. 高置信检索多样性（条件实施）

仅当 Phase0 证明近重复会挤出独立规则点时实施：

- `ruleLibraryId` 硬隔离；
- Phase1 只使用可靠 `derivedSemanticKey`；
- trigram shingle Jaccard；
- 合并前执行 `dedupSafetyVeto`；
- 两遍排序：先全部簇代表，再用次级候选补足 `limit`；
- `enable_diversity` 默认 off，先离线、再灰度；
- 不在本阶段输出 `possibleDisagreement`；
- 不依据 `sourceKind` 自动判断权威。

进入条件：

- 人工抽检证明高置信簇的误合并风险可接受；
- 不出现跨库、跨版本聚类；
- Hit@5/MRR 不退化；
- Top-8 独立规则点覆盖有明确提升；
- 答案事实和引用支持度不退化。

#### 2B. 动态 Evidence Budget

在现有 `EvidenceBudget` 上增加按意图和剩余上下文计算的预算档位，不另建一套工具循环：

- `RULE_FACT`：优先少量精确证据；
- `PROCEDURE`：允许多个连续步骤章节；
- `COMPARE_OPTIONS`：为比较双方分别预留证据；
- `BUILD_ADVICE`：按子主题分配上限，防止单一主题占满预算。

预算值由 Stage 1 数据标定，不在设计阶段直接写死。Agent 最终可读文档上限与 retrieval 返回 `limit`
继续分层管理，不能把 Agent 的 8 条读取上限硬编码进通用检索服务。

### Stage 3：上下文管理

目标：降低长会话重放成本，同时保持规则证据边界。

实施顺序：

1. 建立统一 `ContextBudget`，分配 System、State、Summary、Recent、Evidence 和 Output Reserve。
2. 使用模型 usage 或保守估算进行 Token 计量，替代单纯字符窗口。
3. 扩展现有 `ConversationState`，继续只采信用户明确声明的状态。
4. 超过阈值时生成滚动摘要，始终保留最近若干轮原文。
5. 摘要由浏览器随会话保存，服务端不建立长期对话数据库。
6. 摘要绑定 `libraryId`、`libraryRevision` 和 `summaryVersion`。
7. revision 变化时，旧规则结论摘要失效或要求重新核对。
8. 规则 Query Rewrite 仍优先；只有规则无法稳定补全指代时才调用 LLM fallback。

摘要可以保存：

- 用户确认的角色状态；
- 用户目标和限制；
- 已做出的选择；
- 尚未解决的问题；
- 以前回答过的规则结论及来源 ID/revision，用于提示重新核对。

摘要不能：

- 直接作为本轮规则证据；
- 把助手推测写成用户事实；
- 保存 Agent 中间思考或完整工具结果；
- 在 revision 改变后继续支撑旧结论。

简单规则问题不得因为 Stage 3 固定增加一次摘要或 Rewrite 模型调用。

### Stage 4：受限复杂任务

目标：提升角色创建、构筑、兼职比较和成长路线等复杂问题，不建设通用自治 Agent 平台。

从现有 `query_intent.py` 和 `build_query_plan()` 演进：

1. 扩展规则优先的复杂度判断。
2. 只对明确的多目标问题做 Query Decomposition。
3. Planner 输出受限 Schema，不能生成任意工具或跨规则库任务。
4. 第一版使用串行 Task Executor。
5. 每个子任务拥有独立 Evidence 配额和来源集合。
6. 最终只向 Answer Synthesizer 提交目标、结构化状态、任务结果和已读证据。
7. 只有评测证明串行执行延迟不可接受且任务真正独立时，才考虑有限并发。

第一批支持范围：

- 角色创建步骤；
- 等级构筑；
- 兼职收益与损失；
- 法术、专长和装备组合；
- 成长路线。

不在本阶段引入 Multi-Agent。

## 7. 统一验收门

任何会改变检索、上下文或工具执行的阶段都必须通过以下检查：

### 7.1 功能与回归

- TypeScript 类型检查；
- Web 生产构建；
- Vitest；
- Python App 测试；
- Python Retrieval 测试；
- PF1e 长期集、结构化集和 V2.1 专项集；
- PF1e 答案级多轮题集；
- 必要时增加 GSS 对应题集。

### 7.2 检索质量

- Hit@5 和 MRR 不出现未经批准的退化；
- Top-8 独立规则点覆盖不下降；
- 不发生跨 `ruleLibraryId` 结果污染；
- 显式 FAQ/勘误查询不得压制目标来源。

### 7.3 答案质量

- 必需事实覆盖不下降；
- 引用支持度不下降；
- 未读取来源不能出现在来源抽屉；
- 无依据结论率和幻觉率不升高；
- 多轮追问仍绑定正确规则库和 revision。

### 7.4 成本与可靠性

- 简单问题不固定增加额外 LLM 调用；
- 工具循环仍有确定上限和安全收尾；
- Prompt、Evidence、Summary 和输出预算可观测；
- 超时、限流和裁判失败不会破坏整轮评测；
- 性能收益必须与基线报告比较，不能仅凭主观判断。

## 8. Feature Flag 与回滚

建议为行为变化设置独立开关：

- `enable_diversity`；
- `enable_dynamic_evidence_budget`；
- `enable_conversation_summary`；
- `enable_llm_query_rewrite`；
- `enable_complex_planner`。

要求：

- 新开关默认 off；
- 关闭开关即可恢复上一阶段行为；
- 每个阶段独立提交、独立评测；
- 不同时上线多个无法分别归因的排序/Prompt 改动；
- 数据构建和代码版本均有对应回滚点。

## 9. 明确暂缓与拒绝项

### 暂缓

- 跨会话长期 Memory；
- Planner 并行调度；
- `canonicalRuleKey` 驱动的跨正文/FAQ/勘误关系；
- `possibleDisagreement` 向答案阶段显式透传；
- 图片、扫描 PDF、复杂表格的 OCR/视觉理解；
- 管理员上传发布页面；
- 生产 HTTPS、Tracing、备份和正式发布流水线。

这些项目仍可进入产品 backlog，但不属于 V2.2 第一阶段。

### 当前不做

- Multi-Agent；
- 自动模型路由；
- 不同版本规则库合并；
- 服务端持久化原始对话；
- 为摘要建立服务端长期会话缓存；
- 全请求 LLM Router/Rewrite；
- 为当前规模进行微服务拆分；
- 未经审计直接开启近重复排序。

## 11. Stage 1 完成与下一项实际工作

Stage 0/1 已完成，交付物和数据评审见 `v2.2-stage1-review.md`。数据结论是：

- 不进入检索多样性 Phase1；
- 浏览器历史不是当前 Token 瓶颈；
- 优先处理同轮多次模型决策重放的工具/证据上下文。

下一项开发目标是：

> **进入 Stage 3 的 ContextBudget 第一阶段，只测量并约束同轮工具/决策上下文，不先生成滚动摘要。**

进入下一阶段前保持以下门槛：

1. 简单问题不得新增模型调用；
2. 只有已读证据可以引用；
3. 累计 prompt token、decision/total latency 必须与本次基线比较；
4. 检索和答案通过率不得退化；
5. 滚动摘要继续暂缓，直到长会话历史数据证明需要。

继续不实现近重复排序、滚动摘要、通用 Planner、Memory 或 Multi-Agent。
