## 1. 结论

V2.3 不建设通用 Agent 平台，也不按 Conversation Manager、Planner、Memory、Multi-Agent 的通用模板
整体重构。当前最合适的路线是：

```text
长会话与 revision 基线
  → 动态 Evidence Budget
  → 受限多问题拆解与路由
  → 串行复杂任务执行
  → 按数据决定是否生成滚动摘要
  → 按数据决定是否有限并行
```

其中前三项是 V2.3 主范围；滚动摘要和并行调度是条件项。Memory、Multi-Agent、自动模型路由和
微服务拆分不进入本轮。

## 2. 设计输入

### 2.1 已吸收的通用原则

参考《TRPG Agent 智能体系统改造迭代方案》，继续采用：

- 确定性逻辑优先由代码完成；
- LLM 只作为复杂语义的受限 fallback；
- 简单问题保持直接 RAG，不固定增加模型调用；
- 先控制 Context 和 Evidence，再增加复杂任务规划；
- Planner 第一版使用统一 Executor，不默认 Multi-Agent；
- 最终回答只接收目标、明确状态、任务结果和已读证据；
- 保持模块化单服务，出现独立扩缩容需求后才讨论拆分。

### 2.2 对通用方案的项目化调整

- Conversation Summary 不作为 P0。现有真实样本 History p95 仅 89 token，没有证明跨轮历史是主要成本。
- Evaluation 不放到最后。任何行为阶段必须先扩展对应评测，再实现功能。
- 当前已经有 Intent、Evidence Budget、Answer Synthesizer 和 Agent Loop，不重复建设平行框架。
- 当前已经是 BM25 + Vector + weighted RRF + 结构重排，不把“替换检索引擎”作为默认任务。
- Memory 会改变浏览器本地会话和服务端零持久化边界，必须作为独立产品与隐私决策。

## 3. 当前实现基线

### 3.1 已完成能力

- 对话绑定单一 `libraryId`、系统、版本和创建时 revision；
- `ConversationState` 只从用户明确陈述中提取角色等级、职业组合、兼职、种族、属性、专长、法术和偏好；
- 规则优先的 Query Rewrite 和四类意图：`RULE_FACT`、`PROCEDURE`、`COMPARE_OPTIONS`、`BUILD_ADVICE`；
- `search_rules` / `read_rules` 串行工具循环、重复查询/结果检测、工具和决策上限、安全收尾；
- 搜索、读取文档、Evidence 字符和 Evidence token 固定预算；
- `ContextBudget` 分配 System、State、Recent、Decision Tool、Evidence、Output Reserve；
- 每批工具结果完整展示一次，后续决策只保留 ID/引用回执；
- 只有 `read_rules` 读取并注册的文档可以成为来源；
- 最终回答使用当前问题、明确状态和本轮已读证据的干净上下文；
- Retrieval、Answer、Context、Token、Evidence 和 Latency 评测与聚合报告。

### 3.2 固定质量基线

- PF1E 构建：`20260809T004148Z`；
- 85 题长期检索：Hit@5 90.6%，MRR 0.7351；
- 30 题结构化检索：Hit@5 83.3%，MRR 0.6750；
- MiMo PF1E 答案评测：4 case / 6 轮全部通过，无依据率 0%；
- ContextBudget 后累计 prompt token mean/p95：11,528 / 17,571；
- 总延迟 mean/p95：57.26 / 80.42 秒；
- provider usage 覆盖率：100%。

### 3.3 未解决问题

1. 缺少能证明长会话裁剪、状态保留和 revision 更新行为的正式评测集；
2. `EvidenceBudget` 仍使用同一固定档位，没有根据意图和剩余 Context 分配；
3. 构筑问题只有固定的三方向 Query Plan，没有统一多问题 Schema 和任务级来源集合；
4. Intent 只做规则分类，没有复杂度、是否拆解和是否进入 Planner 的显式路由决策；
5. 没有串行 Task Executor、任务依赖、任务级超时和结构化 Task Result；
6. 没有滚动摘要，但当前也没有数据证明应实现；
7. GSS 只有 Retrieval 金集，没有与 PF1E 同等级的答案级回归集。

## 4. 不可破坏边界

### 4.1 规则证据

- Summary、ConversationState、Query Plan、Route Decision 和 Task Result 都不是规则证据；
- 规则结论只能由本轮 `read_rules` 注册的来源支撑；
- 搜索摘要不能直接进入最终答案作为引用；
- 子任务不能跨 `libraryId`、system、edition 或 revision 混用来源；
- revision 改变后，旧规则结论只能作为待复核线索，不能继续支撑答案。

### 4.2 隐私与存储

- 服务端不持久化原始问题、回答或完整对话；
- 指标不记录问题、答案、规则正文、摘要正文、计划正文或密钥；
- 如实现 Summary，随浏览器会话本地保存，并绑定 `libraryId`、`libraryRevision`、`summaryVersion`；
- 不实现跨会话 Memory，除非另行完成产品授权、删除机制、数据模型和隐私评审。

### 4.3 成本与可靠性

- 简单规则问题不得固定增加 Router、Rewrite、Summary 或 Planner 模型调用；
- 所有循环、子任务、并发、超时和 Evidence 必须有代码上限；
- provider 失败、超时、限流或无效 Schema 不得破坏整轮对话状态；
- 新阶段必须能通过独立 Feature Flag 关闭并恢复上一阶段行为。

## 5. Stage 0：长会话与 revision 评测基线

> 完成于 2026-08-09：确定性契约 3/3、MiMo 真实答案 3/3、来源命中 3/3、无依据率 0%；
> 12/24/48 轮真实 History 为 222/391/737 token 且均未裁剪。发布门满足，Summary 启动条件未满足。

### 5.1 目标

先证明真实缺口，再决定是否生成滚动摘要。Stage 0 只增加评测、指标和必要的测试夹具，不改变线上 Prompt。

### 5.2 评测场景

新增长会话 case，至少覆盖：

- 早期明确角色状态，经过多轮无关问题后再追问；
- 后续用户明确修改职业、等级、种族、专长或法术，最新值覆盖旧值；
- 助手曾经推测但用户未确认的内容不得进入 State；
- 指代“它、这个、刚才第二个方案”在规则能够补全与不能稳定补全两种场景；
- History 超预算时保留最近原文并发出 `context_truncated`；
- 对话创建 revision 与当前规则库 revision 不一致时，前端警告仍有效；
- 未来 Summary 失效的契约测试先行：revision 变化后不得把旧规则结论当证据。

建议分为 12、24、48 轮三个长度档，并区分事实追问、状态修改和无关聊天。

评测契约和命令见 [长会话与 revision 评测](long-conversation-evaluation.md)。

### 5.3 新增指标

- `context.truncationRate`；
- `context.stateFieldCount`；
- `context.historyTokens` 按会话长度分桶；
- `context.revisionMismatch`；
- 状态保留正确率、旧值覆盖正确率、未确认状态误采信率；
- 长会话答案事实、来源匹配、无依据率和总延迟。

指标只记录数量、布尔值、哈希和耗时，不记录字段正文。

### 5.4 进入下一阶段的门

- 长会话评测可重复运行并生成聚合报告；
- 所有 State 只来自用户明确陈述；
- revision 不匹配不会继续使用旧来源支撑新答案；
- 现有 PF1E 6 轮答案基线仍为 6/6；
- 不增加线上模型调用。

### 5.5 Summary 启动条件

只有同时满足以下条件，才能立项 Stage 4：

- History p95 超过 8,000 token，或长会话消息裁剪率超过 5%；
- 裁剪导致状态、指代或答案来源出现可复现退化；
- `ConversationState + Recent Window` 无法用确定性方式修复；
- 摘要额外成本和延迟有独立预算。

未满足时继续使用 State + Recent Window，不实现 Summary。

## 6. Stage 1：动态 Evidence Budget

> 2026-08-10 完成：策略、默认关闭的 Feature Flag、多主题配额、指代追问恢复、专项金集和
> 安全指标已落地；PF1E/GSS 检索门保持基线。经明确授权，MiMo 固定/动态专项均为 5/5，
> 动态 PF1E 回归为 6/6、来源 100%、无依据率 0%，简单事实题成本门通过。

### 6.1 目标

在现有 `EvidenceBudget` 和 `ContextBudget` 上增加唯一的预算策略层，不另建工具循环。

### 6.2 设计

新增纯代码策略，例如：

```python
EvidenceBudgetPolicy.allocate(
    intent,
    context_budget,
    query_plan,
    conversation_state,
) -> EvidenceBudgetProfile
```

`EvidenceBudgetProfile` 至少包含：

```json
{
  "max_searches": 0,
  "max_answer_documents": 0,
  "max_evidence_tokens": 0,
  "topic_allocations": {},
  "policy_version": 2
}
```

预算档位按 Stage 0 和现有真实指标标定，不在设计文档中写死线上数值：

- `RULE_FACT`：少量精确证据，优先单条规则；
- `PROCEDURE`：允许连续步骤章节；
- `COMPARE_OPTIONS`：为双方分别预留 Evidence；
- `BUILD_ADVICE`：按职业能力、属性/专长/法术、兼职收益损失等子主题分配；
- 未知意图回退到当前固定安全预算。

### 6.3 约束

- `max_answer_documents` 与 Retrieval `limit` 分层，不能把 Agent 预算写进通用检索器；
- 单篇超大文档不能挤掉同批次所有较小文档；
- 同一文档只计入一次预算和一次来源注册；
- 子主题未使用的预算可以回收，但不能让单一主题占满全部预算；
- `enable_dynamic_evidence_budget` 默认 off。

### 6.4 验收门

- PF1E Retrieval Hit@5/MRR 不退化；
- PF1E 答案评测 6/6、来源匹配 100%、无依据率 0%；
- GSS Retrieval 22 题不退化；
- 简单事实题的搜索、读取、prompt token 和 total latency 不增加超过 10%；
- Compare/Build 新增专项 case 的关键子主题都有已读证据；
- 关闭 Feature Flag 后行为恢复为当前固定预算。

### 7.1 目标

显式区分单问题、可直接拆分的多问题和需要复杂执行的任务，但不引入通用 Planner。

### 7.2 Route Decision

定义严格 Schema：

```json
{
  "intent": "BUILD_ADVICE",
  "complexity": "simple|compound|complex",
  "need_decomposition": true,
  "need_planner": false,
  "domains": ["class", "feat", "spell"],
  "reason_code": "explicit_multi_goal",
  "router_version": 1
}
```

第一版 Route Decision 完全由代码生成：

- 明确单实体规则事实 → `simple`；
- 明确列举多个独立问句或多个构筑子目标 → `compound`；
- 同时包含目标、约束、多个选择域和成长阶段 → `complex`；
- 无法高置信判断时保持当前直接 Agent Loop，不调用 LLM Router。

### 7.3 Query Decomposition

定义最多 4 个子问题的受限 Schema：

```json
{
  "questions": [
    {
      "id": "q1",
      "question": "...",
      "domain": "class|race|feat|spell|equipment|progression|rule",
      "depends_on": []
    }
  ]
}
```

要求：

- 显式多目标优先用规则拆分；
- 子问题只继承用户明确目标和状态；
- 每个子问题有独立 Evidence 配额和来源集合；
- 子问题结果不能直接作为规则证据；
- 第一版串行执行，不使用并发；
- `enable_query_decomposition` 默认 off。

### 7.4 LLM Fallback 条件

LLM Decomposition 不随 Stage 2 默认上线。只有规则拆分专项集证明复杂表达召回不足时，才新增：

- 严格 JSON Schema；
- 禁止模型直接回答；
- 输入只包含 Current Query、Recent、State，未来可选 Summary；
- Schema 失败或超时回退当前直接 Agent Loop；
- 独立 `enable_llm_query_decomposition`，默认 off；
- 单问题绝不调用。

### 7.5 验收门

- 新增单问题误拆率、多问题覆盖率、子问题平均数和路由耗时；
- 单问题误拆率为 0；
- 显式多问题专项集的目标覆盖率达到 100%；
- 子问题数量不超过 4，工具和 Evidence 总量有全局上限；
- 简单问题模型调用数与当前基线相同；
- PF1E 6 轮答案回归继续 6/6。

> PF1E Adapter，再补齐专长时间线/前提图和法术元数据，并把整答重试改为结构化修补或服务器渲染；
> 完成本地门前不再运行外部 A/B。
> 详见 `complex-task-evaluation.md` 与 `complex-planner.md`。

### 8.1 启动条件

只有 Stage 2 的 `complex` 专项集证明直接 Agent Loop 无法稳定覆盖多个目标时才进入。

启动判定必须排除基础检索漏召回：结构探针和本地来源覆盖仅用于形成 Planner 候选集；只有同一候选
集的真实 Stage 2 答案基线稳定出现条件推理、目标覆盖或预算失败，才允许进入 8.3 实现。

### 8.2 支持范围

第一版只支持：

- 角色创建步骤；
- 等级构筑；
- 兼职收益与损失；
- 法术、专长和装备组合；
- 成长路线。

### 8.3 Plan Schema

Planner 只生成受限计划，不生成任意工具：

```json
{
  "goal": "...",
  "tasks": [
    {
      "id": "t1",
      "type": "rule_research|compare|selection|progression",
      "query": "...",
      "domain": "class|race|feat|spell|equipment|progression|rule",
      "depends_on": []
    }
  ],
  "planner_version": 1
}
```

硬限制：

- 最多 6 个任务；
- 只能使用当前规则库；
- 禁止生成 URL、模型、系统命令或任意工具名；
- 依赖必须构成无环图；
- Schema 无效、超时或任务超限时回退 Stage 2 串行子问题；
- `enable_complex_planner` 默认 off。

### 8.4 Task Executor

第一版按依赖拓扑串行执行：

- 每个任务独立 Evidence 配额和引用注册表；
- 每个任务有 timeout，全局有 deadline；
- 任务失败不污染 ConversationState；
- Task Result 只保存结论状态、缺失字段、来源 ID 和可见摘要；
- 最终 Synthesizer 重新取得已注册 Evidence 正文，不重放各任务工具历史。

### 8.5 Answer Synthesizer

最终输入只包含：

```text
Current User Goal
+ Explicit ConversationState
+ Route Decision
+ Structured Task Results
+ Registered Evidence
```

回答必须分离：

- 规则事实；
- 基于规则的推导；
- 选择建议；
- 收益与损失；
- 适用条件；
- 缺失信息；
- 来源。

### 8.6 验收门

- 复杂任务完成率、平均任务数、失败任务数、Planner/Executor/Final latency 可观测；
- 每条规则事实可追踪到任务和已读来源；
- 未覆盖目标必须显式列入缺失信息；
- 简单问题不进入 Planner；
- Planner 增加的调用和延迟必须与直接 Agent Loop A/B 比较；
- 串行版本质量稳定前不得进入并行。

### 8.7 发布门整改：通用 Fact Ledger 核心与 PF1E Adapter

#### 8.7.1 目标与非目标

真实 MiMo 复测证明第一版 PF1E Fact Ledger 可以拦截部分错误，但严格完成率仍为 0/6，整答重试
还使平均时延和模型 token 显著上升。本节属于 Stage 3 发布门失败后的整改，不是原计划中的新
“Stage 3.3”，也不改变 Stage 4/5 编号。

本轮目标：

- 把 Evidence provenance、事实状态、验证生命周期、结构化修补和安全输出门抽成通用核心；
- 把现有职业、专长、法术、进阶职业和装备解析/校验迁入 PF1E Adapter；
- 在行为等价迁移后，补齐真实失败样本暴露的 PF1E 事实覆盖；
- 保持 Planner、普通 Agent Loop、规则库隔离和流式安全边界不退化。

本轮不做：

- 不设计可表达任意 TRPG 的通用规则 DSL；
- 不为没有真实失败样本的规则系统预建事实类型；
- 不启用跨规则库 Planner，不让一个 Adapter 读取另一规则库证据；
- 不因通用化拆分微服务或搬迁整个 planning/chat 目录。

#### 8.7.2 通用核心边界

通用核心只定义以下协议，不识别“法师”“专长”“法术环级”等规则概念：

```json
{
  "adapter_id": "pathfinder-1e",
  "adapter_version": 1,
  "subject": "character",
  "predicate": "has_option_at_level",
  "value": {"level": 5, "option_type": "feat", "count": 1},
  "value_type": "object",
  "status": "known|unknown|conflicting",
  "derivation": "observed|derived",
  "evidence_refs": ["S3"]
}
```

核心职责：

- 保存类型化 `FactRecord`，并确保每个 `known` / `conflicting` 值绑定已注册 Evidence；
- 保留 `unknown`，禁止用模型常识把缺失字段自动升级为已知；
- 调度 Adapter 的解析器和确定性 Validator，统一输出带路径、严重级别、期望值、实际值和来源的
  `ValidationIssue`；
- 接受只修改失败字段的结构化 patch，重新验证完整草稿；
- 验证通过后才允许渲染/流出，失败时安全拒答且不附虚假来源；
- 只记录版本、数量、状态和耗时指标，不记录事实正文、用户问题或答案。

#### 8.7.3 Adapter 选择与降级

- Adapter 由当前 `LibraryManifest` 的稳定 `id + system + edition` 注册信息选择，禁止根据用户问题
  文本猜测规则系统；
- Adapter 只接收本轮当前规则库通过 `read_rules` 注册的 Evidence；
- PF1E Adapter 第一版承接现有解析器和 Validator，不改变既有判断结果；
- 未注册 Adapter、Adapter 版本不兼容、解析失败或没有可验证事实时，记录原因并跳过硬校验，继续
  当前稳定回答路径；不得套用 PF1E 规则，也不得阻断简单问题；
- 《夕妖晚谣》在没有专属 Adapter 前必须命中上述无 Adapter 降级测试。

#### 8.7.4 PF1E Adapter 整改范围

等价迁移完成后，只根据已经出现的失败样本扩充：

- 所有角色的奇数等级通用专长时间线，以及人类、战士等额外/职业奖励专长来源；
- 专长规范名称、前提图、可选范围和获得等级；
- 法术规范名称、环级、学派、持续时间、豁免与职业法术位节点；
- 角色等级、职业等级、施法者等级、最高法术环级与进阶职业推进的区分；
- 装备价格、伤害、AC、奥术失败率和擅长条件的来源绑定。

#### 8.7.5 结构化修补与输出

不再把整篇自由文本连同错误列表交给模型完整重写。第一版修补协议应：

1. 最终生成器先返回带稳定 claim/section ID 的结构化 `AnswerDraft`；
2. Validator 返回精确失败路径和可修补标记；
3. 只允许模型为失败路径返回有 Schema 的 patch，不得修改已验证事实和来源；
4. 服务器合并 patch 后重新验证完整草稿，最多一次；
5. 验证通过后由确定性 Renderer 生成最终 Markdown 并增量发送；失败则安全拒答。

如果结构化生成或 Renderer 会显著扩大实现，本轮允许先完成“核心 + Adapter 等价迁移”，但不得以
继续整答重试作为发布方案。

#### 8.7.6 实施顺序

1. 固定现有 PF1E 正负样本和真实复测结果，禁止在迁移中移动金线；
2. 定义通用 Fact、Issue、Adapter、Repair Patch 接口和注册表；
3. 将现有 PF1E 解析与校验逐项迁入 Adapter，完成行为等价测试；
4. 增加无 Adapter、错误 Adapter、GSS 隔离和安全降级测试；
5. 扩充 PF1E 时间线、前提图与法术元数据；
6. 实现结构化局部修补和确定性渲染；
7. 完成本地正负样本、全仓回归和成本探针后，再申请真实 MiMo A/B 授权。

## 9. Stage 4：滚动摘要（条件项）

### 9.1 前提

必须满足 Stage 0 的 Summary 启动条件。不能因为通用架构包含 Summary 就直接实施。

### 9.2 数据模型

```json
{
  "summaryVersion": 1,
  "libraryId": "pathfinder-1e",
  "libraryRevision": "...",
  "updatedThroughMessageId": "...",
  "confirmedState": {},
  "goals": [],
  "constraints": [],
  "decisions": [],
  "openQuestions": [],
  "priorRuleReferences": []
}
```

### 9.3 边界

- Summary 随浏览器会话保存，服务端不建长期数据库；
- 只总结即将淘汰的旧消息，始终保留最近原文；
- 助手推测不能进入 `confirmedState`；
- 不保存 Agent 思考、完整工具结果或规则正文；
- `priorRuleReferences` 只是重新检索提示，不是 Evidence；
- revision 变化时旧规则引用失效并要求重新核对；
- 简单问题不得为更新摘要固定增加一次模型调用；
- `enable_conversation_summary` 默认 off。

### 9.4 验收门

- 长会话答案和状态正确率高于纯裁剪基线；
- Summary token + Recent token 明显低于原 History；
- 摘要幻觉、未确认状态误写入和 revision 越界均为 0；
- 摘要失败时可以继续使用 Recent + State；
- 浏览器删除会话会同时删除摘要。

## 10. Stage 5：有限并行（条件项）

只有串行复杂任务的质量已稳定，同时 p95 延迟明确超过发布门，才考虑并行。

允许并行的任务必须：

- 没有依赖；
- 不修改同一状态；
- 使用线程安全工具；
- 不突破 provider 和 Retrieval 限流；
- 共享全局 deadline、并发上限和 Evidence 上限。

第一版只并行 Retrieval/Read 子任务，不并行 Planner 和 Final Synthesizer。任何并行失败都必须能回退串行。
