# TrpgRuleAgent V2 RAG 问题分类与解决记录

更新时间：2026-08-01  
适用分支：`release`  
当前规则库：

- `golden-sky-stories-zh-1-2@20260801T105530Z`
- `pathfinder-1e@20260801T134116Z`

## 1. 文档目的

本文不再按“先做了什么、后来又做了什么”的时间线记录 V2 RAG 改造，而是按故障发生的层级分类。每个问题统一回答七件事：

1. 问题属于哪一层；
2. 用户看到了什么现象；
3. 如何判断问题发生在哪一层；
4. 根因是什么；
5. 使用什么长期方案解决；
6. 如何防止回归；
7. 当前状态如何。

这样做的目的是避免把所有异常都归结为“模型不行”或“RAG 没搜到”。相同的错误提示，可能分别来自规则库路由、文档解析、候选召回、证据读取、答案生成、引用校验或运行环境。

## 2. 问题分类方法

排查时按以下顺序判断：

| 层级 | 核心问题 | 典型判断依据 |
| --- | --- | --- |
| 规则库路由 | 搜的是不是正确的游戏系统和版本 | 当前 `libraryId`、系统别名、问题中的系统术语 |
| 文档解析与切分 | 正确内容是否进入了可检索文档 | 原始 PDF/CHM、父文档、标题路径、表格结构 |
| 候选召回与排序 | 正确父文档是否进入前 K | 离线 Hit@K、MRR、候选列表 |
| 证据读取与 Agent 编排 | 命中的正文是否真的交给最终回答 | 工具轨迹、已读文档 ID、预算和停止原因 |
| 答案生成 | 模型是否依据正文正确作答 | 答案事实、完整性、是否出现无依据推断 |
| 引用与安全输出 | 结论是否被真实来源支持 | 引用 ID 是否属于本轮已读证据 |
| 会话上下文 | 追问是否保留必要任务和选择 | 结构化会话状态、当前目标字段 |
| 运行与供应商 | 代码、数据版本或外部接口是否正常 | PID、提交号、规则修订号、HTTP 错误分类 |

一个简单的判断原则是：

- 搜错规则库，是路由问题；
- 正确内容根本没有被切出来，是解析与切分问题；
- 正确内容存在但没进前 K，是召回或排序问题；
- 已进入候选但没有读正文，是 Agent 编排问题；
- 正文已经读取但回答仍然错，是生成问题；
- 回答正确但来源不支持结论，是引用问题；
- 单轮正确、追问错误，优先检查上下文状态；
- 同一代码本地表现不一致，优先检查运行版本和供应商响应。

## 3. 规则库路由问题

### ROUTE-01：问题属于其他系统，却在当前规则库内反复搜索

**现象**

对话绑定《夕妖晚谣》时询问“你知道魔战士吗”，模型在当前库中反复换词搜索，最后触发工具上限，并返回“规则范围过大”或“请缩小问题”。

**如何定位**

- 当前会话绑定的 `libraryId` 是《夕妖晚谣》；
- 问题术语更可能属于其他规则系统；
- 多次搜索结果为空或高度重复；
- 错误发生在读取到有效正文之前。

**根因**

旧实现把“判断问题属于哪个规则库”交给模型临场处理。模型既不能切换规则库，也没有稳定的停止条件，只能在错误的库里继续搜索。

**长期解决办法**

- 每个会话固定绑定 `libraryId`、系统、版本和发布修订；
- 为规则库维护显式系统名与别名，例如 `PF1E`、`Pathfinder 1E`、`GSS`；
- 明确命中其他系统别名时，在检索前结束当前库流程并提示用户切换；
- 系统归属不明确时允许搜索当前库，但必须受重复查询、空结果和工具预算约束；
- 不允许模型在一次回答中自行跨库混检。

**防回归验证**

- 使用“当前库明确存在”“明确属于其他库”“无法判断归属”三类问题分别测试；
- 断言跨库问题不会调用当前库检索；
- 断言未知问题以证据不足结束，而不是误报“范围过大”。

**状态**：已解决。核心提交：`f079bfd`、`104fefc`、`6feaac8`。

### ROUTE-02：多轮追问只保留实体词，丢失当前任务范围

**现象**

用户先问如何创建角色，再问“有哪几种真身？”。如果只搜索“真身”，会把“变身时露出真身”等无关章节排到前面。

**如何定位**

- 单独看追问文字存在歧义；
- 上一轮已经明确当前任务是“创建角色”；
- 候选中出现词面匹配但任务不匹配的章节。

**根因**

查询改写只看最后一句，没有继承当前任务范围。

**长期解决办法**

- 从用户消息维护结构化 `ConversationState`；
- 当追问实体属于当前任务时，把任务范围加入检索查询；
- 只继承用户明确建立的任务，不为独立问题凭空补充上下文。

**防回归验证**

- 连续测试“创建角色 → 真身种类 → 选择猫”；
- 同时测试没有上文的独立“真身是什么”，确保系统不错误添加创建角色范围。

**状态**：已解决。核心提交：`182a164`、`7e13d47`。

## 4. 文档解析与切分问题

### PARSE-01：PDF 按页切分，命中页面但拿不到完整章节

**现象**

- “如何创建角色”只能召回部分步骤；
- “有哪几种真身”跨第 43、44 页，模型只读到其中一页；
- 猫的特技和弱点跨页后容易混淆；
- 页眉或项目符号污染标题路径。

**如何定位**

- 原始 PDF 中存在正确内容；
- 单页文档只包含答案的一部分；
- 相邻页共同构成一个语义章节；
- 问题不是“完全没搜到”，而是父文档边界不合理。

**根因**

物理页不是规则书的语义边界。旧切分没有表达章节继承、局部标题、跨页列表和表格关系。

**长期解决办法**

- 识别页面标题、继承标题和页面局部标题；
- 保存 `headingPath`、`detectedHeadings`、`localHeadings`、`inheritedHeadings` 和 `structuralBlocks`；
- 父文档保存完整、可引用正文，子块只负责召回；
- 把标题路径加入子块检索文本；
- 跨页章节继承全局标题，短项目标题只在当前页生效。

**防回归验证**

- 对跨页列表、表格和局部标题建立固定检索题；
- 检查父文档正文完整性，而不只检查 Hit@K；
- 用连续问答验证列表是否完整。

**状态**：已解决文本型 PDF 的主要结构问题。图片、扫描页和复杂图表仍未覆盖。核心提交：`6326c11`、`75802ef`、`dbe8e35`。

### PARSE-02：数字表格行或短项目被误识别为标题

**现象**

表格数字行、项目名称或“吓一跳”“打架”等短文本成为全局标题，并污染后续页面的路径和排序。

**如何定位**

- 查看导入审计中的标题层级；
- 对照原始页面确认文本只是表格行或局部项目；
- 检查错误标题是否延续到后续页面。

**根因**

仅按字体、长度或孤立文本判断标题，没有区分表格内容、局部标签和跨页章节标题。

**长期解决办法**

- 排除纯数字和表格形态文本；
- 将特定短项目标记为页面局部标题；
- 在导入报告中保留启发式警告，方便人工审计；
- 用结构属性而不是单一长度阈值决定标题层级。

**防回归验证**

- 为数字表格行和局部项目增加单元测试；
- 检查下一页不继承局部标题。

**状态**：已解决。核心提交：`75802ef`、`dbe8e35`。

### PARSE-03：PF1e CHM 的子章节、表格和导航空壳没有被正确表达

**现象**

- 大型 CHM 页面中的职业变体、子章节或表格被塞在同一个父文档中；
- 精确问题虽然能搜到大页面，但目标段落排名不稳定；
- 拆分后出现多个正文只有“职业变体”的重复文档，发布校验失败。

**如何定位**

- 原始 CHM 页面内有清晰标题层级和 HTML 表格；
- 旧父文档粒度明显大于单一规则主题；
- 重复内容检查发现 9 个仅含同一导航标签的文档；
- 正确内容存在，但结构信息没有进入索引。

**根因**

旧导入器主要按文件切分，没有充分使用 HTML 标题和表格。结构化拆分的第一版又把重复导航文字误当作有效章节正文。

**长期解决办法**

- 按 CHM 标题层级生成语义父文档；
- 表格按“表头 + 数据行”生成结构化检索块；
- 保留 `legacyParentId`，兼容既有人工评测标注；
- 过滤正文不超过 80 字、且所有文本行都只是已知标题的导航空壳；
- 发布前执行精确重复内容检查，发现重复则拒绝发布。

**防回归验证**

- 30 题结构化专项集覆盖表格、子章节和职业变体；
- 增加“重复导航标题应被丢弃”的单元测试；
- 发布门要求重复正文组为 0。

**状态**：已解决并发布。当前 PF1e 为 2,498 个父文档、33,585 个检索子块。核心提交：`b10c1c6`、`7c9b4db`、`5286972`、`3cf29b2`。

## 5. 候选召回与排序问题

### RETRIEVE-01：正确内容存在，但没有进入 Agent 可读的前 K

**现象**

早期 PF1e 的敏捷属性用途、全防御动作和火把照明等问题没有进入前 5；某些表格或职业变体问题的正确章节排名偏后。

**如何定位**

- 在结构化文档中能找到正确答案；
- 离线评测的 `relevantIds` 没出现在前 K；
- 因此问题发生在召回或排序阶段，而不是生成阶段。

**根因**

- 只使用单一检索信号；
- 中文术语、标题路径与正文词面没有共同参与排序；
- 大文档内的精确小节缺少独立结构；
- 表格数据没有携带表头语义。

**长期解决办法**

- 向量召回与中文 BM25 并行；
- 使用加权 Reciprocal Rank Fusion 合并排名；
- BM25 使用中文单字、双字词元和英文单词；
- 将标题路径和表格表头加入检索表示；
- 使用轻量来源优先级，但不让它覆盖精确内容匹配；
- 用人工标注集选择参数，不通过向语料注入答案刷分。

**防回归验证**

- PF1e 长期集 85 题：Hit@5 100%，MRR 0.8676；
- PF1e 结构化专项集 30 题：Hit@5 100%，MRR 0.9361；
- 《夕妖晚谣》22 题：Hit@5 100%，MRR 0.9773。

**状态**：当前验收集内已解决。新增规则和新问题仍需持续扩充评测集。

### RETRIEVE-02：宽泛查询扩展改善一个问题，却破坏精确查询

**现象**

为“如何创建角色”增加同义词和标题奖励后，《夕妖晚谣》召回改善，但 PF1e 的“能力值如何购点”被错误扩展成通用角色创建问题。

**如何定位**

- 改动前精确问题正常，增加宽泛扩展后回归；
- 错误候选与“创建角色”相关，但不回答“购点”；
- 属于查询规划和重排冲突，不是文档缺失。

**根因**

同一个扩展策略同时用于宽泛任务问题和具体规则子问题。

**长期解决办法**

- 引入确定性的 `RetrievalCoordinator`；
- 对“创建/建立”等同义词做有限扩展；
- 用标题路径联合重排实体和规则类别；
- “有哪些、列出、是什么”等直接查询裁剪弱结构候选；
- 属性、技能、专长、装备、法术、弱点、特技、生命值和购点等具体子主题禁止宽泛扩展。

**防回归验证**

- 每次调整查询扩展，同时运行宽泛任务题和精确子主题题；
- 不只看 Hit@5，还比较 MRR 和前几名候选变化。

**状态**：已解决。核心提交：`6cf5c63`、`dbe8e35`。

### RETRIEVE-03：精确命中的候选被通用裁剪规则误删

**现象**

直接查询已经找到高相关候选，但结构裁剪把正确首位候选移除，导致后续读取不到最佳证据。

**如何定位**

- 原始混合召回首位正确；
- 经过协调器裁剪后正确候选消失；
- 问题发生在召回之后、读取之前。

**根因**

直接查询的弱候选裁剪没有保护已经形成明确证据优势的候选。

**长期解决办法**

- 为精确证据领先者设置保护条件；
- 结构裁剪只删除弱相关候选，不覆盖明确的内容匹配；
- 把该行为纳入结构化专项评测。

**防回归验证**

- 比较协调器处理前后的首位候选；
- 30 题结构化专项集必须保持全量命中。

**状态**：已解决。核心提交：`5286972`。

## 6. 证据读取与 Agent 编排问题

### AGENT-01：不同模型使用工具的方式不同，导致循环或触发上限

**现象**

Agnes 更容易重复换词搜索、连续搜索不读取或重复提交工具；MiMo 和 DeepSeek 在相同问题上不一定触发上限。错误提示曾表现为“规则检索未能在安全范围内完成”。

**如何定位**

- 候选检索本身没有异常；
- 工具轨迹包含重复查询、重复结果或连续无读取；
- 不同模型在相同数据上的工具轨迹明显不同。

**根因**

旧控制器默认模型会严格遵循 `search_rules → read_rules → finish_answer`。实际上，工具协议兼容只保证格式兼容，不保证各模型采用相同的决策策略。

**长期解决办法**

- 服务端每轮只执行一个工具；
- 检测重复查询、重复结果、重复读取和连续无效调用；
- 限制连续“只搜索不读取”的次数；
- 到达决策上限时根据已读证据安全收尾；
- 将检索预算做成服务端策略，不依赖模型自律；
- 不针对单个供应商堆叠临时提示词。

**防回归验证**

- 用不同模型执行相同的有证据、无证据和跨库问题；
- 断言最终只能落入“有已读证据并回答”或“无证据并明确结束”；
- 断言不会把工具预算耗尽误报成问题范围过大。

**状态**：服务端收敛机制已完成。核心提交：`104fefc`、`6feaac8`、`ae50534`。

### AGENT-02：搜索已经命中，但模型没有读取正文就结束

**现象**

模型调用 `search_rules` 后直接调用 `finish_answer`，或者停止输出。候选中已有正确页面，最终却回答“没有可靠依据”。

**如何定位**

- 搜索候选包含正确父文档；
- 本轮已读证据列表为空；
- 停止发生在 `read_rules` 之前。

**根因**

证据闭环依赖模型主动调用读取工具，而不同模型可能提前结束。

**长期解决办法**

- 搜索后提前结束且没有已读证据时，由服务端补读最近候选；
- 模型提交无效文档 ID 时，改读本轮真实候选；
- 重复读取已注册文档时，继续读取尚未使用的候选；
- 补读仍受章节数和证据字符预算约束；
- 搜索摘要永远不能替代父文档正文。

**防回归验证**

- 模拟搜索后立即结束、无工具输出和无效 ID；
- 断言进入答案生成前已有真实可引用正文。

**状态**：已解决。核心提交：`704a907`、`bfb511a`。

## 7. 答案生成问题

### GENERATE-01：模型返回中间计划、拒绝信息或空输出

**现象**

DeepSeek 曾把“让我继续搜索后续的创建步骤内容”作为最终回答；供应商也可能返回拒绝信息、临时错误文本或空内容。

**如何定位**

- 已经存在可读证据；
- 最终文本没有回答用户问题，而是过程性计划、拒绝或空白；
- 因此不是召回问题，而是生成质量门失败。

**根因**

旧实现把供应商返回的任何文本都当成可展示的最终答案。

**长期解决办法**

- 在服务端缓冲最终答案；
- 检测拒绝、临时错误、空回答和未完成的过程性文本；
- 首次失败时携带恢复指令重新生成一次；
- 连续失败则返回稳定的生成错误；
- 不合格输出不得附带来源。

**防回归验证**

- 为拒绝、空输出、“让我继续搜索”等文本建立自动测试；
- 断言这些输出不会进入正常答案事件。

**状态**：已解决。核心提交：`1ee4cee`。

### GENERATE-02：正文已经读取，但模型凭位置推断不存在的字段关系

**现象**

用户选择猫的基本特技“一团毛球”后询问弱点，模型曾声称它对应“随心所欲”。原文只说明猫有哪些基本特技和弱点，没有说明两者按位置对应。

**如何定位**

- 检索和读取的页面正确；
- 原文没有模型声称的对应关系；
- 错误发生在模型解释证据时，因此属于生成问题。

**根因**

模型把相邻表格、出现顺序或并列会话状态误解成约束关系。

**长期解决办法**

- 用户选择的不同字段默认只是并列状态；
- 除非规则明确说明，不得根据位置、顺序或名称相似推断关系；
- 将会话状态拆成“本轮目标字段”“实体约束”“其他并列状态”；
- 根据实体约束回答目标字段，其他并列状态不自动缩小答案范围。

**防回归验证**

- 连续测试“真身=猫 → 基本特技=一团毛球 → 可选弱点”；
- 答案必须列出猫的全部可选弱点，并明确基本特技不构成限制。

**状态**：已解决。核心提交：`452d08c`、`a5c0a4f`。

### GENERATE-03：不同模型答案表现不同，但不能用模型特判修复

**现象**

相同检索结果在 MiMo、DeepSeek 和 Agnes 上可能分别生成完整答案、过程性回答或证据不足。Agnes 的工具循环问题尤其明显。

**如何定位**

- 固定相同规则库、候选和正文；
- 更换模型后结果发生变化；
- 说明剩余差异主要位于工具决策或生成层。

**根因**

OpenAI 兼容接口统一了请求格式，但没有统一模型的工具策略、停止行为和证据理解能力。

**长期解决办法**

- 将路由、预算、重复检测、候选补读和引用注册放在服务端；
- 模型只负责有限的查询意图和基于证据的自然语言生成；
- 用供应商无关的答案质量门处理空输出和过程性回答；
- 模型配置只保留必要差异，例如 Agnes 官方 `enable_thinking=false`，不写改变业务语义的专用分支。

**防回归验证**

- 答案级评测记录事实、来源、多轮状态、错误事件和工具成本；
- 当前 PF1e 新修订按用户决定只使用 MiMo 验收，4 组、6 轮全部通过；
- 本轮未用 Agnes 或 SenseNova 作为 PF1e 发布门。

**状态**：架构层已解决；模型质量仍需通过持续评测管理。

## 8. 引用与安全输出问题

### CITE-01：答案带有来源，但来源未必支持正文

**现象**

模型可能漏写引用，也可能在拒绝信息或过程性回答后附上已注册来源，使界面看起来像“这段话有规则依据”。

**如何定位**

- 检查引用 ID 是否属于本轮真实读取的文档；
- 检查引用内容是否支持对应结论；
- 区分“搜索候选”和“已读证据”。

**根因**

旧实现没有严格区分候选、已读正文、模型生成文本和最终允许展示的来源。

**长期解决办法**

- 只有 `read_rules` 成功读取的父文档才能注册为引用；
- 搜索摘要不能成为最终依据；
- 模型漏写引用时，只能从本轮已读来源补充；
- 未通过生成质量门的输出不附带任何来源；
- 结构化拆分通过 `legacyParentId` 保持人工标注与来源映射稳定。

**防回归验证**

- 断言引用集合是已读证据集合的子集；
- 答案级验收同时检查事实和来源，不以“有脚注”代替“脚注支持结论”。

**状态**：已解决。核心提交：`ae50534`、`1ee4cee`、`5286972`。

## 9. 会话上下文问题

### CONTEXT-01：简单滑动窗口无法稳定保留用户选择

**现象**

“创建角色 → 选择猫 → 选择一团毛球 → 询问弱点”的连续对话中，不同模型会遗忘选择、错误关联字段或用错误范围检索。

**如何定位**

- 单轮问题可以正确回答，多轮追问失败；
- 所需信息存在于历史消息，但没有结构化表达；
- 更换模型后历史理解结果不一致。

**根因**

关键状态完全依赖模型反复阅读原始滑动窗口，既浪费 Token，也无法保证稳定解释。

**长期解决办法**

- 保留必要原始历史，同时从用户消息提取结构化状态；
- 当前记录任务、真身、职业、种族、角色类型、特技、弱点、技能和专长等明确选择；
- 将状态分别用于查询规划和最终答案；
- 明确区分目标字段、实体约束和其他并列状态。

**防回归验证**

- 建立多轮答案用例，不只测试单条问题；
- 检查后续查询是否带入正确任务和实体，但没有引入无依据约束。

**状态**：第一版已完成。对话摘要、Token 计量和长期记忆仍待实现。核心提交：`182a164`、`7e13d47`、`a5c0a4f`。

## 10. 运行环境与供应商问题

### RUNTIME-01：健康检查正常，但实际运行的是旧代码或旧规则版本

**现象**

新服务因 8000 端口被旧进程占用而启动失败，但 `/health` 仍然可访问。真实模型测试因此误用了旧代码。

**如何定位**

- 查看端口监听 PID 和进程工作目录；
- 对比预期提交、规则修订号与 `/api/bootstrap` 返回值；
- 不以单纯 HTTP 200 判断版本已经更新。

**根因**

存活状态和版本身份是两个不同问题。旧进程仍然健康，不代表新构建已经生效。

**长期解决办法**

- 重启时只终止经过命令和工作目录确认的 PID；
- 启动后检查监听日志和 Bootstrap 规则修订；
- 后续在就绪或版本接口暴露安全的应用提交号和规则库修订号；
- 自动验收在版本不匹配时直接失败。

**防回归验证**

- 当前 Web 已确认加载 PF1e `20260801T134116Z` 和《夕妖晚谣》`20260801T105530Z`。

**状态**：操作流程已解决；应用提交号尚未暴露。

### PROVIDER-01：供应商限流被误判为检索失败

**现象**

SenseNova / DeepSeek 返回 HTTP 429 时，用户可能看到类似规则检索失败的笼统提示。

**如何定位**

- 检查模型 HTTP 状态码和请求 ID；
- 如果请求没有获得模型响应，就不能归因于召回或生成；
- 将外部接口错误与 Agent 预算错误分开。

**根因**

旧错误模型没有区分限流、超时、连接、鉴权、请求拒绝、证据预算和内部异常。

**长期解决办法**

- 为模型调用增加独立超时和重试配置；
- 使用稳定错误码，例如 `model_rate_limited`；
- 安全日志通过请求 ID 关联调用链；
- 供应商限流不计入 RAG 质量缺陷。

**防回归验证**

- 模拟 429、401、超时和连接失败；
- 断言每种错误进入正确分类，不返回“范围过大”。

**状态**：已解决。按当前决定，SenseNova 真实接口验收不作为本阶段发布门。

## 12. 后续新增问题的记录模板

以后不要只写“模型回答错了”或“优化了 RAG”。请按下面模板追加：

```md
### <分类-ID>：<一句话问题>

**现象**

用户输入、实际输出和预期输出是什么。

**如何定位**

通过什么证据判断它属于路由、解析、召回、读取、生成、引用、上下文或运行问题。

**根因**

造成问题的稳定机制是什么，而不是只描述某次模型表现。

**长期解决办法**

服务端、数据管线、评测或产品边界如何改变。

**防回归验证**

增加了什么单元测试、离线问题集、答案级用例或运行版本检查。

**状态**：未处理 / 处理中 / 已解决 / 部分解决。
```

如果一次用户失败跨越多个层级，应拆成多条记录。例如：

- 正确规则库没有选中：记录为 `ROUTE`；
- 切分后正确章节没有进入前 5：另记为 `RETRIEVE`；
- 正确正文已经读取但模型仍然答错：另记为 `GENERATE`；
- 来源编号与正文不一致：另记为 `CITE`。

不要用最后看到的错误提示直接判断故障层，必须结合路由结果、候选列表、已读证据、最终答案和运行版本共同定位。
