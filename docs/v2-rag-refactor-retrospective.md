# TrpgRuleAgent 从问题发现到 V2 RAG 收口的完整复盘

更新时间：2026-08-01  
适用分支：`release`  
当前规则库修订：`golden-sky-stories-zh-1-2@20260801T105530Z`

## 1. 文档目的

本文记录本项目从“整体实现偏重、重构方向不明确”开始，到 Web/Python 主链路、第二套规则库、Agent 工具收敛、结构化 RAG 和多轮状态管理逐步落地的全过程。

每一阶段都按以下顺序记录：

1. 发现了什么问题；
2. 为什么会出现；
3. 采取了什么措施；
4. 验证时又暴露了什么问题；
5. 后续如何继续修正。

按照当前决定，SenseNova / DeepSeek 的真实接口验收不再作为本阶段完成条件。文中仍保留其限流现象，但不把它计入项目缺陷或验收阻塞。

## 2. 最初的问题：项目范围和架构过重

### 2.1 发现的问题

项目最初同时包含：

- Node Agent Runtime；
- BYOK Gateway；
- 旧 Web 调试界面；
- 微信小程序骨架；
- Python 检索服务；
- 多种客户端接入方式；
- 用户自行配置模型与服务端配置模型两套思路。

对于“先服务少量可信用户、验证规则问答是否可靠”这个目标，上述范围过大。大量精力被分散到多宿主、多鉴权模式和基础设施抽象上，核心问题——规则是否能被稳定检索并正确回答——反而不够突出。

### 2.2 采取的措施

产品范围被收缩为：

- 暂停微信小程序，只做 Web；
- 面向少量可信用户；
- 首版使用共享密码，不做完整用户系统；
- 模型统一由服务端配置，但前端允许在多个已配置模型之间选择；
- 规则上传和发布只允许管理员操作；
- 支持完全不同的游戏系统；
- 同一系统的不同版本必须拆成不同规则库；
- 不处理房规，只以管理员发布的规则为准；
- 首期支持文本型 PDF 和 CHM；
- Markdown 在前端安全渲染，用户看到格式效果而不是 `**` 等原始标记；
- 引用采用 `[S1]`、`[S2]` 对应的脚注/来源形式。

### 2.3 结果

正式产品入口收敛为：

- `apps/web-next`：React Web；
- `services/app-python`：共享密码、模型调用、Agent、规则检索、引用和静态资源托管；
- `services/retrieval-python`：导入、切块、索引和检索。

旧 Node/BYOK、旧 Web 和小程序实现继续保留，但被明确标记为遗留链路，等待新链路实际验收后一次删除。

## 3. 第一版主链路完成后：稳定性不足

### 3.1 发现的问题

Web/Python 第一版可以运行，但还存在典型的“演示可用、长期运行不稳”问题：

- 模型超时、限流、鉴权失败和连接失败没有稳定分类；
- 请求失败时不容易定位具体请求；
- 模型可能漏写引用；
- Agnes 的 thinking 处理依赖输出后过滤；
- 缺少完整的存活和就绪探针；
- 启动时只检查部分环境变量；
- 手机浏览器尚未完整验收。

### 3.2 采取的措施：V1 稳定性收口

- 为每个模型增加独立的请求超时和重试配置；
- 将模型错误分类为超时、限流、连接、鉴权、请求拒绝、证据预算和内部错误；
- 每次聊天生成请求 ID，并在响应与安全日志中关联；
- 增加 `/health` 和 `/ready`；
- 启动时校验完整 YAML 和所有模型环境变量；
- Agnes 改用官方 OpenAI 兼容参数 `chat_template_kwargs.enable_thinking=false`；
- 模型必须先读取证据才能回答；正文漏写引用时，只能补充本轮真实读取过的来源；
- 完成 390×844 手机视口下的对话、模型选择、Markdown、输入区和来源抽屉验收。

### 3.3 新暴露的问题

稳定性收口之后，问题从“服务是否能工作”转向“不同模型是否会以完全不同的方式使用工具”。尤其 Agnes 更容易：

- 重复换词搜索；
- 连续搜索但不读取；
- 直接提交不存在或属于上一轮的文档 ID；
- 在达到模型轮次或工具预算时返回误导性错误；
- 把“让我继续搜索”这样的中间计划当成最终回答。

## 4. 第二套规则库加入后：跨系统隔离和 Agent 工具循环问题

### 4.1 发现的问题

导入《夕妖晚谣》作为第二套真实规则后，单规则库时代隐藏的问题开始出现：

- 当前对话必须固定绑定一个系统和版本；
- 明显属于其他系统的问题不应在当前库中盲目检索；
- 不同模型对空结果和工具调用的处理差异很大；
- Agnes 会反复检索空结果，最终触发上限，并被错误提示为“问题范围过大”；
- 同一问题在 MiMo、DeepSeek、Agnes 上可能分别表现为正常回答、过程性回答或证据不足。

典型问题是“你知道魔战士吗”。当对话绑定《夕妖晚谣》时，它可能属于其他系统；旧实现却允许模型在当前库中反复换词搜索。

### 4.2 采取的措施：规则库边界

- 每个对话固定绑定 `libraryId`、系统、版本和发布修订；
- 新建对话必须明确选择规则库；
- Bootstrap、聊天和来源读取均按 `libraryId` 隔离；
- 为规则库增加显式别名；
- 明显提到其他规则库或系统时，不调用当前库检索，直接提示切换；
- 系统归属不明确的问题仍可搜索当前库，但必须遵守证据流程；
- 规则库构建与发布分离，只有显式 `publish` 才原子更新 `current`。

### 4.3 采取的措施：服务端工具循环控制

相关提交：

- `104fefc fix: enforce convergent tool loops`
- `6feaac8 fix: finish safely at agent decision limit`
- `ae50534 fix: separate retrieval planning from final answers`
- `704a907 fix: recover grounded evidence across follow-up turns`

具体措施包括：

- 服务端每轮只执行一个工具，忽略模型并行提交的额外工具；
- 检测重复查询、重复结果、重复读取和连续无效工具调用；
- 限制连续“只搜索不读取”的次数；
- 到达总决策上限时，使用已读取证据收尾，而不是抛出工具上限错误；
- 搜索摘要不能直接作为最终规则依据，必须读取父文档；
- 最终答案阶段与工具规划历史分离，只传入最后问题、会话状态和已读取证据；
- 模型首次跳过工具时，由服务端按最后一条用户问题执行搜索；
- 模型提交不存在的文档 ID 时，服务端改读本轮真实搜索候选；
- 模型重复读取已注册文档时，服务端继续读取尚未使用的候选。

### 4.4 结果

Agnes 不再因为反复检索而把问题误报为“范围过大”。即使不同模型的工具调用风格不同，服务端也负责让流程收敛到以下两个安全结果之一：

1. 有已读取证据：生成带真实引用的回答；
2. 没有可读证据：明确返回证据不足，不生成伪引用。

## 5. 新问题：模型输出本身可能不安全或不完整

### 5.1 发现的问题

即使工具流程正确，供应商仍可能返回：

- 拒绝信息；
- “让我继续搜索”之类未完成计划；
- 临时服务错误文本；
- 空输出。

旧实现可能把这些内容和已经注册的来源一起返回，从界面上看就像“拒绝信息也有规则依据”。

### 5.2 采取的措施

提交：`1ee4cee fix: reject unsafe model output before citations`

- 最终答案先在服务端缓冲；
- 检测供应商拒绝、临时错误、空回答和未完成过程性文本；
- 首次失败时用恢复指令重新生成一次；
- 连续两次失败则返回稳定错误说明；
- 被拒绝或未完成的输出永远不附带来源。

### 5.3 结果

“模型说了什么”和“服务端允许什么成为规则结论”被正式分离。引用只属于通过质量门的规则回答。

## 6. 新问题：原始 PDF 按页切分，检索能命中页面却不理解结构

### 6.1 发现的问题

用户测试“我应该怎么创建一个角色”“有哪几种真身”等问题时，三个模型仍会出现：

- 命中相邻但不完整的页面；
- 只回答“让我继续搜索后续步骤”；
- 真身列表跨第 43、44 页，模型只读到其中一页；
- 猫的基本特技和弱点表格在第 51、52 页，模型容易混淆；
- 页眉、表格数字行或项目符号被误判为章节标题；
- 标题状态错误地泄漏到后续页面。

根因不是单纯的向量模型，而是父文档和子块缺少可靠的章节结构。

### 6.2 采取的措施：结构化 PDF 导入与切块

相关提交：

- `6326c11 feat: add structure-aware PDF retrieval chunks`
- `75802ef fix: reject numeric table rows as PDF headings`
- `dbe8e35 fix: stabilize structured PDF retrieval`

具体措施：

- 规范化 PDF 布局文本和异常空白；
- 识别页面标题、继承标题和局部项目标题；
- 为父文档保存 `headingPath`、`detectedHeadings`、`localHeadings`、`inheritedHeadings` 和 `structuralBlocks`；
- 子块按结构块生成，并把标题路径加入检索文本；
- 纯数字、表格行和规则描述不再被误判为标题；
- `⚫`、`•` 等短项目标题只在当前页生效，不污染后续页面；
- 跨页章节保留全局标题上下文。

### 6.3 验证时暴露的新问题

第一轮结构化切分把某些短项目标题处理成了全局标题。例如“吓一跳”“打架”等局部项目可能影响下一页路径。修正为页面局部标题后，标题结构才稳定下来。

新的《夕妖晚谣》索引包含：

- 154 个父文档；
- 488 个结构化检索子块；
- 159 个 PDF 页面；
- 59 个表格；
- 23 条需保留审查的启发式警告。

图片、扫描页和复杂图表理解仍未包含在本轮文本型 RAG 范围内。

## 7. 新问题：有结构仍不等于排序正确

### 7.1 发现的问题

结构化切块完成后，召回率提高，但仍有两类排序问题：

- 宽泛问题“如何创建角色”需要优先命中“化形的建立方式”；
- 具体问题“能力值如何购点”不能因为包含“创建角色”就被宽泛扩展，否则 PF1e 的精确召回会下降。

### 7.2 采取的措施：检索协调器

提交：`6cf5c63 feat: coordinate and rerank structured retrieval`

- 在混合检索外增加确定性的 `RetrievalCoordinator`；
- 对同义词进行有限扩展，例如“创建/建立”“基本特性/基本特技”；
- 使用标题路径进行实体与规则类别联合重排；
- 对“有哪些、是什么、列出”等直接查询裁剪弱结构候选；
- 对宽泛角色创建问题增加章节标题奖励；
- 对属性、技能、专长、装备、法术、弱点、特技、生命值和购点等具体子问题禁止宽泛创建扩展。

### 7.3 验证时暴露的新问题

最初的角色创建扩展让《夕妖晚谣》表现更好，却使 PF1e 的“能力值购点”被错误扩大为通用创建问题。加入“具体子主题不扩展”后，PF1e 回归恢复到基线。

最终离线结果：

| 规则库 | 评测数 | Hit@5 | MRR |
| --- | ---: | ---: | ---: |
| 《夕妖晚谣》1.2 | 22 | 100% | 0.9773 |
| PF1e | 85 | 96.5% | 0.8255 |

## 8. 新问题：检索正确，但多轮对话丢失用户选择

### 8.1 发现的问题

对话流程中出现了以下失败：

1. 用户问“我应该怎么创建一个角色”；
2. 用户选择“猫”作为真身；
3. 用户选择“一团毛球”；
4. 用户追问“我现在可以选择什么弱点”。

旧实现主要依赖原始消息滑动窗口。模型必须自行从历史中重新理解“当前任务、真身、已选特技”，不同模型的稳定性差异很大。

### 8.2 采取的措施：显式会话状态

提交：`182a164 feat: preserve explicit conversation choices`

新增 `ConversationState`，只从用户消息提取：

- 当前任务，例如“创建角色”；
- 真身、正体、职业、种族、角色类型；
- 基本特技、追加特技、弱点、技能、专长等明确选择。

提取出的状态用于：

- 丰富后续检索查询；
- 给最终答案提供结构化上下文；
- 避免依赖模型从长历史中反复猜测用户选择。

### 8.3 验证时暴露的新问题：追问失去任务范围

Agnes 在回答完角色创建后，面对“有哪几种真身？”只按“真身”搜索，导致“变身时露出真身”等章节参与竞争。虽然第 43 页进入候选，跨页列表仍可能不完整。

### 8.4 采取的措施：任务范围继承

提交：`7e13d47 fix: retain task scope for entity follow-ups`

- 当已有任务为“创建角色”，后续又询问真身、职业、种族等实体选项时，将任务范围带入检索；
- “有哪几种真身？”实际按“创建角色中的真身种类”检索；
- 不为没有历史任务的独立问题凭空补充任务。

修正后，第 43、44 页稳定排在该追问的前两位，Agnes 能完整列出狐、狸、猫、狗、兔、鸟、鼠。

## 9. 新问题：模型把并列状态错误理解为字段对应关系

### 9.1 发现的问题

在以下追问中：

> 我选择基本特性为一团毛球，我现在可以选择什么弱点？

Agnes 曾错误声称“一团毛球”对应“随心所欲”。原文只说明：

- “一团毛球”是猫的基本特技；
- 猫有六个弱点；
- 每个弱点和一个追加特技对应。

原文没有说基本特技与弱点按行、按位置或按顺序对应。

### 9.2 第一层措施：禁止无依据关联

提交：`452d08c fix: prevent unsupported state correlations`

最终答案生成器增加约束：

- 用户选择的不同字段默认只是并列状态；
- 除非规则原文明示，不得声称一个字段限制另一个字段；
- 不得根据表格位置、出现顺序或名称相似自行推断对应关系。

### 9.3 第一层措施后的新表现

Agnes 不再编造错误对应关系，但变得过度保守，改为回答“证据不足”，没有利用第 52 页已经完整列出的六个猫弱点。

这说明单纯禁止错误推断还不够，系统还需要告诉模型：用户真正询问的目标字段是什么。

### 9.4 第二层措施：目标字段与并列状态分离

提交：`a5c0a4f fix: separate answer targets from parallel state`

`ConversationState` 现在为最终回答生成字段解释：

- 目标字段：本轮真正要回答的字段，例如“弱点”；
- 实体约束：决定规则范围的实体，例如“真身=猫”；
- 其他并列状态：已经选择但不自动限制目标字段的内容，例如“基本特技=一团毛球”。

最终提示明确要求：

- 根据实体约束回答目标字段；
- 其他并列状态不缩小目标字段范围；
- 只有规则明确说明时才能建立字段约束。

最终 Agnes 能正确回答：猫可从好动天性、游手好闲、敏感舌头、遇水则慌、随心所欲、张牙舞爪中选择弱点；“一团毛球”不限制弱点选择。

## 10. 新问题：模型搜索后提前结束，证据候选被丢弃

### 10.1 发现的问题

Agnes 的工具调用并不完全稳定。有时它会：

1. 正常调用 `search_rules`；
2. 搜索已经命中正确页面；
3. 没有调用 `read_rules`，直接调用 `finish_answer` 或停止输出。

旧控制器只在部分停止原因下自动补读候选，因此会出现“检索明明命中第 51 页，最终却说没有可靠依据”。

### 10.2 采取的措施：服务端证据闭环

提交：`bfb511a fix: read candidates when models stop early`

- 模型搜索后直接结束且尚无已读证据时，服务端读取最近搜索候选；
- 模型搜索后无工具输出且尚无证据时，同样读取候选；
- 默认最多补读前 4 个候选，并继续遵守答案最多 8 个章节和证据字符预算；
- 补读完成后才进入最终答案阶段。

### 10.3 结果

证据流程不再依赖某个模型是否严格遵循 `search_rules → read_rules → finish_answer`。模型负责提出搜索意图，服务端负责保证进入最终回答前确实存在可引用正文。

## 11. 验收过程中发现的运行环境问题

### 11.1 发现的问题

第一次发布新规则库后，端口 `8000` 已被旧 Python 进程占用。新进程启动失败，但健康检查仍能访问旧进程，因此最初一轮真实模型测试实际上使用了旧代码。

这导致 Agnes 的第一次错误回答一度看起来像是新实现仍未生效。

### 11.2 采取的措施

- 使用端口监听检查定位旧进程；
- 明确停止旧 PID；
- 重新启动当前 `release` 代码；
- 从启动日志确认新 PID 成功监听；
- 再执行真实模型验收；
- 后续每次涉及运行时代码变化，都先停止当前受控会话，再启动新服务。

### 11.3 经验

## 14. 这轮改造得出的核心结论

### 14.1 不能把可靠性寄托在某一个模型会正确使用工具

不同模型会搜索、读取、重复调用、跳过工具或提前结束。长期稳定性必须来自服务端状态机、预算和证据闭环，而不是为某个模型写临时提示词补丁。

### 14.2 RAG 质量不只是切块大小问题

本轮真正有效的改进来自：

- 父文档保持完整可引用内容；
- 子块只负责召回；
- 章节路径进入检索文本；
- 局部标题与跨页标题分开；
- 宽泛问题和具体子问题采用不同扩展策略；
- 会话任务范围参与查询；
- 最终回答只使用已读证据。

因此不应继续用“统一调大或调小 chunk size”作为主要优化手段。

### 14.3 对话状态不能只靠滑动窗口

原始历史仍然保留，但关键用户选择需要结构化为任务、实体和字段状态。这样既能减少模型重复理解历史的 Token，也能避免不同模型对相同历史作出不同推断。

### 14.4 表格正确提取不代表模型一定正确理解关系

第 52 页的 Markdown 表格已经正确表达“弱点 ↔ 追加特技”，模型仍可能把相邻的基本特技误当成对应项。因此还需要答案阶段的关系约束和字段语义，而不能只依赖 PDF 解析。
